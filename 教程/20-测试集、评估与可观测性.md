## 3. 通俗解释与精确技术定义

**人话**：

- 测试是"给自己上保险"：改一行代码，知道有没有弄坏口径。
- 评估是"给自己打分"：固定一组的题，看现在能答成什么样。
- 可观测性是"给自己留证据"：出错时能说清"哪一步、用了多久、调了几次工具"。

**定义与分层**：

| 层 | 输入 | 判定方式 | 本项目做法 |
| --- | --- | --- | --- |
| 确定性层 | 固定数据 + 固定问题 | 断言具体数值/状态 | `pytest tests/`，不 mock 数据库与计算 |
| 模型行为层 | 真实模型 + 提示词 | 人工 rubric 或 LLM-as-judge，记录工具序列 | `scripts/check_model.py` 探测能力；`eval/run_eval.py` 记录但不判分 |

**三条容易犯的错**：

1. 用 mock 掉数据库的测试证明"SQL 口径正确"——被 mock 掉的正是被测对象；
2. 用"确定性用例通过"宣传"模型效果"——两者不相关；
3. 用单次运行的时间戳结果当"性能"，却不记录机器与版本。

### 5.3 一个"值得学"的测试（节选 `tests/test_metrics.py`）

```python
def test_t10_comparison_matches_ground_truth_delta(conn, ground_truth):
    """总差额与独立标准答案脚本的结果完全一致（整数分）。"""
    result = compare_months(conn, "2026-09", "2026-08")
    expected = ground_truth["comparison_2026_09_vs_2026_08"]
    assert result.delta_net_cents == expected["delta_net_cents"]

def test_t12_zero_base_returns_none_pct(conn):
    """基期为 0 时变化率无定义，返回 None 并标记 base_zero。"""
    result = compare_months(conn, "2026-09", "2026-08", region_ids=("R_NE",))
    assert result.previous.net_cents == 0
    assert result.base_zero is True
    assert result.pct_change is None
```

为什么这两条值得学：第一条把"生产实现"与"独立实现"对齐（两边同时错才会漏）；第二条把"零基数"写成了可执行断言，而不是文档里的一句话。

### 5.4 一个可观测性断言（节选 `tests/test_workflow.py`）

```python
def test_t20_usage_reports_no_model_calls(runtime):
    turn = runtime.invoke_turn(MAIN_QUESTION)
    assert turn["usage"]["model_calls"] == 0   # 纯规则模式不应调用模型
    assert "elapsed_ms" in turn["usage"]
```

这类断言能抓住"偷偷调模型"的回归——比性能数字更有价值。

## 8. 失败与边界实验

1. **删掉 `conftest.py` 里的临时目录**：测试会写进仓库 `data/`，观察 `test_api.py` 是否因共享库出现串扰。结论：测试隔离是设计出来的。
2. **把 `InMemorySaver` 换成 `SqliteSaver` 跑全套**：可能变慢并留下检查点文件；对比时长，理解"测试用内存、演示用文件"。
3. **让标准答案脚本 import `queries.py`**：它不再独立，"交叉验证"退化为"自己验证自己"。这是**最隐蔽**的退化。
4. **删掉一条边界用例**（例如真零）：`pytest` 仍全绿，但你失去了对"真零 vs 无记录"的保护。结论：覆盖率不等于保护力。
5. **只跑模型不管确定性**：配置模型后让模型直接算差额，再与 `compare_months` 对比——你会发现模型算错时无法定位，因为数字没有来源。这正是本项目坚持"程序算数"的原因。

## 10. 复盘问题与参考答案、下一步

**Q1：为什么不 mock 数据库？**
A：本项目的核心风险是**口径**（退款归属、零基数、空月），这些只能在真实 SQLite 上验证。mock 会把风险点换成"mock 是否忠实"。

**Q2：`status_matched` 能当准确率吗？**
A：不能。它只说明"工作流状态符合预期"，不说明答案措辞、工具选择、数字解释是否正确。模型行为要单独评估。

**Q3：测试全绿就说明系统可靠吗？**
A：不。它说明"已写下的断言成立"。没写的边界（例如并发审批、超大月份范围）仍然可能出错。

**Q4：为什么要保留 `docs/verification.md` 这种"自曝其短"的文档？**
A：因为它把"没跑过"变成可追踪的风险，而不是隐藏的谎言。面试里能讲清"我验证了 A/B，没验证 C 及其原因"，比"全部通过"更可信。
