## 3. 通俗解释与精确技术定义

### 3.1 为什么需要结构化输出

你要的是“`2026-09` 和 `2026-08` 这两个月”，不是一段“好的，2026 年 9 月相比 8 月……”的文字。文字要再写正则去抠，抠错了还静默。

结构化输出（structured output）就是：**让模型把答案填进一张表格**，程序拿表格字段做事。

### 3.2 但“合法 JSON”不等于“业务正确”

这是本单元最重要的一句话。三层完全不同的东西：

| 层 | 问题 | 谁负责 | 例子 |
| --- | --- | --- | --- |
| 语法层 | 是不是合法 JSON | 模型/解析器 | 少了引号 → 解析失败 |
| 模式层 | 字段类型对不对 | Pydantic | `net_sales_cents: "很多"` → 校验失败 |
| 业务层 | 值说得通吗 | **你的代码** | 月份 `2026-13`、地区 `华东他区`、时期晚于今天 |

模型只能保证前两层“大概率”，第三层必须你自己写规则。

### 3.3 术语（双语）

- **模式（schema）**：字段名、类型、约束的声明。
- **校验（validation）**：检查数据是否满足模式与规则。
- **归一化（normalization）**：把“9月/九月/09月”统一成 `2026-09` 这类规范形式。
- **结构化输出（structured output）**：模型按 schema 返回对象（而非自由文本）。
- **约束（constraint）**：如正则、枚举、范围。
- **失败即拒绝（fail closed）**：不确定就报错/澄清，不猜。

### 3.4 业务约束清单（本项目口径）

一条用户问题解析成 `QuestionSpec` 时，至少要满足：

1. `current_month` / `previous_month` 形如 `YYYY-MM`，月份 01～12。
2. 月份落在数据范围 `2025-01`～`2026-09` 内，否则给“超出数据范围”的提示。
3. `dimension ∈ {region, product, month, channel, unknown}`；`channel` 明确“不支持分析”。
4. `metric ∈ {net_sales, gross_sales, refunds}`；默认为 `net_sales`。
5. 缺年份 → `needs_clarification=True`，澄清消息必须含数据范围。
6. 地区名不在已知列表 → 澄清可用地区（不是编一个）。

> 这 6 条来自工程规格 5.2 与第 4 节口径，属于**项目设计选择**（规则是项目定的），不是官方 API 约束。

**关键设计**：项目里“时间/指标/地区解析”由 `parse_question` 用规则完成，模型不参与。理由：

1. 时间解析是**确定性任务**，规则可以 100% 覆盖并写单元测试。
2. 模型可能把“九月”解析成 2025-09，且错得很自信。
3. 面试时可以清楚地说“我把确定的事交给代码，把不确定的事交给模型”。

代价：规则要维护中文数字表（一…十二）、相对时间（本月/上月/今年/去年）、地区别名；遇到没见过的说法会澄清而不是理解。这是**可接受的代价**——澄清比猜错便宜。

模型的结构化输出在本项目里有明确位置：`invoke_structured` 只用于**可选**场景（例如从一段长资料里抽取“指标定义”片段并生成引用），且输出后必须做引用真实性校验。

## 5. 文件、完整代码、配置与命令

### 5.1 定义 schema：Pydantic v2

```python
from pydantic import BaseModel, ConfigDict, Field, field_validator

MONTH_PATTERN = r"^\d{4}-(0[1-9]|1[0-2])$"


class QuestionSpecModel(BaseModel):
    """模型/规则都产出这个形状；字段含义与工程规格 5.2 一致。"""

    model_config = ConfigDict(extra="forbid")  # 多出来的字段直接拒绝，别静默丢弃

    raw: str = Field(description="用户原始问题")
    current_month: str = Field(pattern=MONTH_PATTERN, description="本期月份 YYYY-MM")
    previous_month: str | None = Field(default=None, pattern=MONTH_PATTERN)
    regions: list[str] = Field(default_factory=list, description="region_id 列表，如 R_EAST")
    dimension: str = Field(default="region", description="region|product|month|channel|unknown")
    metric: str = Field(default="net_sales", description="net_sales|gross_sales|refunds")
    wants_comparison: bool = False
    asks_refund_definition: bool = False
    needs_clarification: bool = False
    clarification: str | None = None

    @field_validator("dimension")
    @classmethod
    def dimension_must_be_known(cls, value: str) -> str:
        allowed = {"region", "product", "month", "channel", "unknown"}
        if value not in allowed:
            raise ValueError(f"dimension 必须是 {sorted(allowed)} 之一，实际是 {value!r}")
        return value
```

三个要点：

- `pattern=` 在 Pydantic v2 里是正则约束（会生成 JSON Schema，模型能“看到”）。
- `extra="forbid"`：模型多编一个字段时立刻报错，而不是悄悄丢掉。**项目选择**：宁可报错，不要静默。
- `field_validator`：模式层管不了的枚举，用自定义校验。

### 5.4 关键认知：模型不会帮你校验业务

模型给你 `month="2026-13"` 时，如果 schema 用 `pattern` 约束，Pydantic 会拒绝；但如果模型给你 `month="2026-09"`、而用户其实问的是 2025 年，schema **无法发现**。业务校验必须单独写。

### 5.5 实验：完整的“解析 → 校验 → 归一化”链（一步步搭出来）

这个实验**不需要密钥**：它把“模型会输出的坏数据”手工喂给校验层，这正是单元 03 的核心训练。分 6 步搭出三层防线（模式层 → 业务层 → 归一化），最终与仓库 `教程/实验/03_validate_spec.py` 完全一致。每一步都能离线跑。

#### 步骤 1：模式层 schema——第一道墙

**这一步解决什么**：模型（或任何上游）给你的 payload 可能缺字段、多字段、格式不对。pydantic 模型把“合法长什么样”写成代码，非法输入在门口就被挡下。

新建 `教程/实验/03_validate_spec.py`：

```python
"""单元 03 实验（步骤 1）：模式层 schema。"""

from __future__ import annotations

import sys

from pydantic import BaseModel, ConfigDict, Field, ValidationError, field_validator

MONTH_PATTERN = r"^\d{4}-(0[1-9]|1[0-2])$"


class QuestionSpecModel(BaseModel):
    """问题解析结果的结构。字段口径见工程规格 5.2。"""

    model_config = ConfigDict(extra="forbid")

    raw: str = Field(min_length=1, description="用户原始问题")
    current_month: str = Field(pattern=MONTH_PATTERN, description="本期月份 YYYY-MM")
    previous_month: str | None = Field(default=None, pattern=MONTH_PATTERN)
    regions: list[str] = Field(default_factory=list)
    dimension: str = Field(default="region")
    metric: str = Field(default="net_sales")
    wants_comparison: bool = False
    asks_refund_definition: bool = False
    needs_clarification: bool = False
    clarification: str | None = None

    @field_validator("dimension")
    @classmethod
    def check_dimension(cls, value: str) -> str:
        allowed = {"region", "product", "month", "channel", "unknown"}
        if value not in allowed:
            raise ValueError(f"dimension 必须是 {sorted(allowed)} 之一，实际 {value!r}")
        return value

    @field_validator("metric")
    @classmethod
    def check_metric(cls, value: str) -> str:
        allowed = {"net_sales", "gross_sales", "refunds"}
        if value not in allowed:
            raise ValueError(f"metric 必须是 {sorted(allowed)} 之一，实际 {value!r}")
        return value


if __name__ == "__main__":
    good = {"raw": "2026 年九月销售额", "current_month": "2026-09"}
    print("正常输入:", QuestionSpecModel.model_validate(good))
    bad = {"raw": "2026年13月", "current_month": "2026-13"}
    try:
        QuestionSpecModel.model_validate(bad)
    except ValidationError as exc:
        for error in exc.errors():
            print(f"模式层拒绝 - 字段 {error['loc']}：{error['msg']}（类型 {error['type']}）")
```

**逐行讲解**：

- `Field(pattern=MONTH_PATTERN)`：`2026-13` 这种“月份格式对、数值不对”的正则一眼识破（`1[0-2]` 只允许 01–12）。
- `ConfigDict(extra="forbid")`：**多出来的字段直接拒绝**。模型自作聪明加个 `confidence: 0.98`？挡下。宽松接受未知字段是数据污染的起点。
- `field_validator` 是“字段级自定义规则”：`dimension`/`metric` 是**枚举**，正则表达不了“集合成员”，用校验器写。
- `errors()` 返回结构化错误列表（字段、消息、类型）——**给人看的错误才值钱**，这就是后面 `show_case` 打印器的原料。

**运行与观察**：

```text
正常输入: raw='2026 年九月销售额' current_month='2026-09' previous_month=None regions=[] dimension='region' metric='net_sales' …
模式层拒绝 - 字段 ('current_month',)：String should match pattern '^\d{4}-(0[1-9]|1[0-2])$'（类型 string_pattern_mismatch）
```

#### 步骤 2：模式层的边界——它挡不住“合法的错”

**这一步解决什么**：`2027-01` 完全符合模式（格式对、月份合法），但**数据范围里没有它**——模式层管“形状”，管不了“业务事实”。先写业务异常类型和月份归一化，为业务层做准备。

```python
class BusinessRuleError(ValueError):
    """业务规则不通过（模式层合法，但业务上不接受）。"""


DATA_MIN_MONTH = "2025-01"
DATA_MAX_MONTH = "2026-09"

CN_DIGITS = {
    "一": 1, "二": 2, "三": 3, "四": 4, "五": 5, "六": 6,
    "七": 7, "八": 8, "九": 9, "十": 10, "十一": 11, "十二": 12,
}


def normalize_month_token(text: str) -> str | None:
    """把“9月/九月/09月”这类token归一化成两位月份；无法识别返回 None。"""
    cleaned = text.strip().replace(" ", "")
    arabic = re.fullmatch(r"(0?[1-9]|1[0-2])月", cleaned)
    if arabic:
        return f"{int(arabic.group(1)):02d}"
    for cn, number in CN_DIGITS.items():
        if cleaned == f"{cn}月":
            return f"{number:02d}"
    return None
```

（文件头部补 `import re`。临时验证：）

```python
    print("-- 归一化自测 --")
    for token in ("9月", "九月", "09月", "十二 月", "13月"):
        print(f"  {token!r:>8} → {normalize_month_token(token)}")
```

**逐行讲解**：

- `BusinessRuleError` 继承 `ValueError`：调用方可以只抓 ValueError 一网打尽，也可以精确抓业务错——**异常类型是接口的一部分**。
- `normalize_month_token` 处理三类真实输入：阿拉伯（9月）、中文（九月）、带空格（十二 月）；`13月` 返回 `None`——**归一化失败不是异常**，调用方决定怎么处置（本项目：触发澄清）。
- 为什么放在模式层之外：归一化是**改写**不是**判定**，职责分开，测试才好写。

**运行与观察**：

```text
-- 归一化自测 --
     '9月' → 09
    '九月' → 09
    '09月' → 09
 '十二 月' → 12
    '13月' → None
```

#### 步骤 3：三条业务规则——范围、顺序、枚举

**这一步解决什么**：把“数据范围 2025-01～2026-09、本期晚于上期、地区只有五个”这些**业务事实**写成可执行的检查。

```python
def check_month_in_range(month: str) -> None:
    """业务校验 1：月份必须在数据范围内。"""
    if not (DATA_MIN_MONTH <= month <= DATA_MAX_MONTH):
        raise BusinessRuleError(
            f"月份 {month} 超出数据范围 {DATA_MIN_MONTH}～{DATA_MAX_MONTH}；"
            "请确认是否指其他年份。"
        )


def check_period_order(current: str, previous: str | None) -> None:
    """业务校验 2：本期必须晚于上期；同时不允许相同。"""
    if previous is None:
        return
    if previous >= current:
        raise BusinessRuleError(f"上期 {previous} 必须早于本期 {current}。")
    check_month_in_range(previous)
    check_month_in_range(current)


KNOWN_REGIONS = {
    "R_EAST": "华东", "R_NORTH": "华北", "R_SOUTH": "华南",
    "R_SW": "西南", "R_NE": "东北",
}


def normalize_region(token: str) -> str:
    """业务校验 3：地区必须是已知 5 个之一，支持“华东/华东地区/R_EAST”。"""
    cleaned = token.strip().replace("地区", "").replace("大区", "")
    if cleaned in KNOWN_REGIONS:
        return cleaned
    for region_id, name in KNOWN_REGIONS.items():
        if cleaned == name or cleaned == region_id:
            return region_id
    raise BusinessRuleError(
        f"无法识别地区 {token!r}；可用地区：{', '.join(f'{k}({v})' for k, v in KNOWN_REGIONS.items())}"
    )
```

**逐行讲解**：

- `DATA_MIN_MONTH <= month <= DATA_MAX_MONTH`：`YYYY-MM` 格式的字符串**字典序就是时间序**——步骤 1 的模式层保证了格式，这里才能直接比字符串。**下层约束是上层技巧的前提**。
- `previous >= current`（而不是 `>`）：把“上期 == 本期”也挡掉——用户问“九月比九月”多半是口误，值得一次明确报错而不是算出 0。
- `normalize_region` 是**校验 + 归一二合一**：认识就返回规范 ID（`华东地区` → `R_EAST`），不认识就报错并列出全部可选项——错误消息本身是给用户的提示词。
- 注意 `dimension` 里有 `channel` 但**没有**渠道数据：这是故意的——模式层放行，上层路由判“不支持”（单元 08），各层只管自己该管的事。

#### 步骤 4：串成完整校验链 + 错误展示器

**这一步解决什么**：三层各就各位后，入口只留一个函数；再配一个把“输入 → 结果”打印清楚的展示器，让每个测试用例的输出口径一致。

```python
def validate_spec(payload: dict) -> QuestionSpecModel:
    """完整校验链：模式层 → 业务层 → 归一化。"""
    spec = QuestionSpecModel.model_validate(payload)
    check_period_order(spec.current_month, spec.previous_month)
    spec.regions = [normalize_region(item) for item in spec.regions]
    return spec


def show_case(name: str, payload: dict) -> None:
    print(f"\n--- {name} ---")
    print("输入：", json.dumps(payload, ensure_ascii=False))
    try:
        spec = validate_spec(payload)
    except ValidationError as exc:
        print("模式层拒绝：")
        for error in exc.errors():
            print(f"  - 字段 {error['loc']}：{error['msg']}（类型 {error['type']}）")
        return
    except BusinessRuleError as exc:
        print(f"业务层拒绝：{exc}")
        return
    print("通过：", spec.model_dump())
```

（文件头部补 `import json`、`import sys`、`from datetime import date`。）

**逐行讲解**：

- `validate_spec` 的三行就是三层防线的**执行顺序**：先模式（最便宜、最快）、再业务（要查规则）、最后归一化（改写数据）。**顺序反了会把脏数据洗白**。
- `except ValidationError` 写在 `except BusinessRuleError` 前面？不需要——两者没有继承关系，顺序无关；但**分开抓**让错误报告能说出“谁拒绝的”。
- `spec.regions = [...]` 直接改模型字段：pydantic v2 默认允许赋值。归一化发生在校验之后，是“改写”不是“判定”。

"""单元 03 实验：结构化输出 + 业务校验。

用法（在 ops-assistant 目录执行）：uv run python ../教程/实验/03_validate_spec.py

from __future__ import annotations

import json
import re
import sys
from datetime import date

from pydantic import BaseModel, ConfigDict, Field, ValidationError, field_validator

MONTH_PATTERN = r"^\d{4}-(0[1-9]|1[0-2])$"
DATA_MIN_MONTH = "2025-01"
DATA_MAX_MONTH = "2026-09"

CN_DIGITS = {
    "一": 1, "二": 2, "三": 3, "四": 4, "五": 5, "六": 6,
    "七": 7, "八": 8, "九": 9, "十": 10, "十一": 11, "十二": 12,
}


class QuestionSpecModel(BaseModel):
    """问题解析结果的结构。字段口径见工程规格 5.2。"""

    model_config = ConfigDict(extra="forbid")

    raw: str = Field(min_length=1, description="用户原始问题")
    current_month: str = Field(pattern=MONTH_PATTERN, description="本期月份 YYYY-MM")
    previous_month: str | None = Field(default=None, pattern=MONTH_PATTERN)
    regions: list[str] = Field(default_factory=list)
    dimension: str = Field(default="region")
    metric: str = Field(default="net_sales")
    wants_comparison: bool = False
    asks_refund_definition: bool = False
    needs_clarification: bool = False
    clarification: str | None = None

    @field_validator("dimension")
    @classmethod
    def check_dimension(cls, value: str) -> str:
        allowed = {"region", "product", "month", "channel", "unknown"}
        if value not in allowed:
            raise ValueError(f"dimension 必须是 {sorted(allowed)} 之一，实际 {value!r}")
        return value

    @field_validator("metric")
    @classmethod
    def check_metric(cls, value: str) -> str:
        allowed = {"net_sales", "gross_sales", "refunds"}
        if value not in allowed:
            raise ValueError(f"metric 必须是 {sorted(allowed)} 之一，实际 {value!r}")
        return value


class BusinessRuleError(ValueError):
    """业务规则不通过（模式层合法，但业务上不接受）。"""


def normalize_month_token(text: str) -> str | None:
    """把“9月/九月/09月”这类token归一化成两位月份；无法识别返回 None。"""
    cleaned = text.strip().replace(" ", "")
    arabic = re.fullmatch(r"(0?[1-9]|1[0-2])月", cleaned)
    if arabic:
        return f"{int(arabic.group(1)):02d}"
    for cn, number in CN_DIGITS.items():
        if cleaned == f"{cn}月":
            return f"{number:02d}"
    return None


def check_month_in_range(month: str) -> None:
    """业务校验 1：月份必须在数据范围内。"""
    if not (DATA_MIN_MONTH <= month <= DATA_MAX_MONTH):
        raise BusinessRuleError(
            f"月份 {month} 超出数据范围 {DATA_MIN_MONTH}～{DATA_MAX_MONTH}；"
            "请确认是否指其他年份。"
        )


def check_period_order(current: str, previous: str | None) -> None:
    """业务校验 2：本期必须晚于上期；同时不允许相同。"""
    if previous is None:
        return
    if previous >= current:
        raise BusinessRuleError(f"上期 {previous} 必须早于本期 {current}。")
    check_month_in_range(previous)
    check_month_in_range(current)


KNOWN_REGIONS = {
    "R_EAST": "华东", "R_NORTH": "华北", "R_SOUTH": "华南",
    "R_SW": "西南", "R_NE": "东北",
}


def normalize_region(token: str) -> str:
    """业务校验 3：地区必须是已知 5 个之一，支持“华东/华东地区/R_EAST”。"""
    cleaned = token.strip().replace("地区", "").replace("大区", "")
    if cleaned in KNOWN_REGIONS:
        return cleaned
    for region_id, name in KNOWN_REGIONS.items():
        if cleaned == name or cleaned == region_id:
            return region_id
    raise BusinessRuleError(
        f"无法识别地区 {token!r}；可用地区：{', '.join(f'{k}({v})' for k, v in KNOWN_REGIONS.items())}"
    )


def validate_spec(payload: dict) -> QuestionSpecModel:
    """完整校验链：模式层 → 业务层 → 归一化。"""
    spec = QuestionSpecModel.model_validate(payload)
    check_period_order(spec.current_month, spec.previous_month)
    spec.regions = [normalize_region(item) for item in spec.regions]
    return spec


def show_case(name: str, payload: dict) -> None:
    print(f"\n--- {name} ---")
    print("输入：", json.dumps(payload, ensure_ascii=False))
    try:
        spec = validate_spec(payload)
    except ValidationError as exc:
        print("模式层拒绝：")
        for error in exc.errors():
            print(f"  - 字段 {error['loc']}：{error['msg']}（类型 {error['type']}）")
        return
    except BusinessRuleError as exc:
        print(f"业务层拒绝：{exc}")
        return
    print("通过：", spec.model_dump())

    print("\n== 归一化演示 ==")

            "current_month": "2026-09",
            "previous_month": "2026-08",
            "regions": [],
            "dimension": "region",

    show_case(

        {"raw": "2026年13月销售额", "current_month": "2026-13"},

    show_case(

    show_case(

### 5.6 和项目的对应关系

| 实验里的东西 | 项目里的对应 |
| --- | --- |
| `QuestionSpecModel` | `domain/question.py` 的 `QuestionSpec`（frozen dataclass，字段一致） |
| `normalize_month_token` | `parse_question` 内部的月份识别（`9月/九月/09月`） |
| `check_month_in_range` | `parse_question` 的 `min_month` / `max_month` 参数 |
| `normalize_region` | `parse_question` 的 `known_regions` 匹配 + 澄清 |
| `BusinessRuleError` | 项目里不抛给用户，而是转成 `clarification` / `route="fail"` |
| `validate_spec` | 项目里“校验 + 归一化 + 错误信息”三步的骨架 |

注意最后一行差异：**实验里抛异常，项目里转成可读提示**。因为项目面向终端用户，异常堆栈不是答案。

> **项目设计选择**：`QuestionSpec` 用 `frozen=True` 的 dataclass 而不是 Pydantic 模型，因为它是**内部计算用的不可变值对象**，不需要从 JSON 反序列化的灵活性；而 API 请求体、工具参数用 Pydantic。代价是两套风格并存，需要在 `spec: dict` 边界做一次 `asdict()` / 手写转换。

## 8. 失败与边界实验（至少 3 个）

### 实验 8.1：让模型输出中文月份数字（比较 mschema 与业务校验）

把 `current_month` 的 `pattern` 删掉，改为普通 `str`，然后传入 `"九月"`。

预期（未在本环境执行）：模式层放行，`validate_spec` 的 `check_month_in_range` 里字符串比较 `"九月" > "2026-09"` 为真，抛 `BusinessRuleError`——**但错误原因是“超出范围”，不是“格式”。“格式错误被误报成范围错误”**。

**要理解的点**：校验层要把“格式”与“范围”分开报，否则用户会收到误导性提示。

### 实验 8.2：`pattern` 与中文数字冲突

保留 `pattern`，传入 `"2026-9"`（少一位）。

预期（未在本环境执行）：`string_pattern_mismatch`。

**要理解的点**：模型经常输出 `2026-9` 这种“人类写法”。正确做法是在提示词里给格式示例，并在校验失败后**重试一次**（带错误信息），而不是放宽校验。

### 实验 8.3：小数金额

如果把金额字段定义成 `net_sales_cents: int`，传入 `1286500.5`。

预期（未在本环境执行）：Pydantic v2 的 `int` 默认拒绝带小数部分的浮点，报 `int_from_float` 类错误。

**要理解的点**：金额必须整数分；这一条由类型系统兜住，比手动 `round()` 可靠。

### 实验 8.4：`with_structured_output` 在不支持工具调用的模型上

```python
structured = model.with_structured_output(QuestionSpecModel)
structured.invoke([HumanMessage(content="解析：2026年九月销售额")])
```

预期（未在本环境执行）：可能抛 `NotImplementedError` / 供应商错误，或返回 `None`。

**要理解的点**：这就是为什么单元 01 要先探测能力。失败时应有降级方案：提示词约束 + 手写解析 + 校验（单元 03 的 5.1 模式），而不是让整个程序崩。

### 实验 8.5：把 `raw` 设为空字符串

`min_length=1` 会拒绝。

**要理解的点**：空输入应在最外层就被挡住，不要一路传到模型再浪费一次调用。

## 10. 复盘问题与参考答案、下一步

### Q1：既然模型能输出 JSON，为什么还要 Pydantic？

**参考**：模型输出的是**字符串**，能不能解析、字段对不对、类型对不对都要程序检查。Pydantic 把“检查”变成声明式的：写一次 schema，解析、校验、生成 JSON Schema 一次完成。没有它，你会散落几十个 `if not isinstance(...)`。

### Q2：`with_structured_output` 和“手写 JSON 解析”怎么选？

**参考**：取决于供应商能力与可控性。`with_structured_output` 省事，但行为依赖底层（tool calling / JSON mode），出错时原因不透明；手写“提示词 + `model_validate_json` + 失败重试”可控、可测试，但要多写代码。**项目设计选择**：项目对“必须确定”的数据（月份、指标）用规则；对“可选增强”（资料抽取）用 `invoke_structured` 并加引用校验。

### Q3：为什么地区名要归一化成 `R_EAST`？

**参考**：数据库里用 `region_id` 做主键，展示用 `region_name`。如果程序各层有的地方用中文名、有的用 id，就会出现“查不到但看起来正常”。归一化到 id 后，查询、聚合、过滤都用同一套值。这是**项目设计选择**，代价是每次输入都要过一次映射表。

### Q4：校验失败后要不要让模型重试？

**参考**：可以重试，但必须**有次数上限**并把错误信息带回去（“你上次输出 `2026-9`，必须是 `YYYY-MM`，请重试”）。无上限重试会烧钱且可能死循环。项目里的预算（`max_steps`）会兜住这类循环，见单元 08。

### Q5：为什么“猜一个默认月份”是严重错误？

**参考**：因为错误不会被发现。报告会正常生成、数字看起来合理、用户不会质疑，但分析对象完全错了。宁可返回澄清，也不要猜——**澄清的成本是一次追问，猜错的成本是一份错报告加一次信任损失**。
