## 3. 通俗解释与精确技术定义

### 3.1 一句类比

把这一轮问答想成一家小店的**流水线**：前台先听清客人要什么（`understand`），不清楚就追问（`clarify`）；要查账就先翻账本（`data`），要解释规则就先翻制度手册（`knowledge`）；算账的人只按公式算（`compute`），写报告的人只按模板填（`draft`），店长签字后才真的存档（`review → export`）。

**模型在这条流水线上的位置很尴尬**：它既不是前台，也不是会计，更不是店长。它最多是一个"文字润色工"——而且它改出来的字里只要出现一个数字，整段就被扔掉（见 3.5）。

### 3.2 精确一点：workflow 和 agent 的分界

> **官方事实**：LangGraph 官方文档把"workflow"和"agent"作为两种不同的编排形态来介绍——workflow 的路径由代码预先编排（节点与边是写死的），agent 的路径由模型动态决定（调用哪些工具、循环几轮）。链接见第 2 节，核对日期 2026-10-19。

> **教学简化**：下面这张表是我为了讲清楚做的压缩版，不是官方原文的分类表。

| 维度 | Workflow（本项目主链路） | Agent（本项目的第二条路线） |
| --- | --- | --- |
| 谁决定下一步做什么 | 代码（条件边 + `route` 字段） | 模型（返回 tool_calls，循环执行） |
| 路径是否可预测 | 可枚举，最多十来步 | 不可枚举，取决于模型 |
| 出错怎么查 | 看 `trace`，一步步对着节点查 | 看消息列表，容易断片 |
| 适合什么 | 有固定口径、要审计、要能被测试的业务 | 开放探索、工具多、路径不确定的问答 |
| 在本项目的入口 | `workflow/graph.py` 的 `build_graph()` | `agent/tools.py` 的 `make_tools()` + 单元 05 的 `create_agent` |

**本项目两条路线共用同一批底层函数**（这是理解整个项目的关键）：

```
                    ┌─────────────────────────────┐
   create_agent ───▶│  agent/tools.py (6 个 @tool) │──┐
   （模型选工具）    └─────────────────────────────┘  │
                                                      ├──▶ data/queries.py
                    ┌─────────────────────────────┐  │    domain/metrics.py
   graph 主链路 ───▶│  workflow/nodes.py           │──┘    knowledge/qa.py
   （代码定顺序）    └─────────────────────────────┘
```

> **项目设计选择**：工作流这一侧**直接调用** `queries.py` / `metrics.py` / `qa.py`，**不**经过 `@tool` 包装，也**不**让模型决定调哪个。原因不是"工具没用"，而是：审计要求每个数字都能追到一条 SQL、每个错误都能追到一个节点；一旦把选工具的权限交给模型，同一句话两次运行可能走不同路径，报告就无法复现。工具层留给另一条路线（自由问答）用。

### 3.3 本项目里到底谁决定什么

这张表是整单元的核心，建议抄一遍：

| 决策点 | 谁决定 | 代码位置 |
| --- | --- | --- |
| 先知识检索还是先取数 | **代码**：`route == "data"` 且问题命中口径关键词才改走 `knowledge` | `workflow/nodes.py:835` |
| 缺时间范围怎么办 | **代码**：澄清，绝不猜年份 | `workflow/nodes.py:814` |
| 取哪两个月 | **代码**：`parse_question` + 跨轮继承 `last_spec` | `workflow/nodes.py:735` |
| 用哪个指标 / 哪个维度 | **代码**：`spec.metric` / `spec.dimension`（含用户偏好兜底） | `workflow/nodes.py:1297` |
| 数字是多少 | **代码**：`queries.py` 取数 + `compare_months` 计算 | `workflow/nodes.py:1327` |
| 报告长什么样 | **模板**：`render_analysis_report` 纯渲染 | `workflow/nodes.py:1680` |
| 要不要落盘 | **人**：`interrupt()` + `resume_turn` | `workflow/nodes.py:1826` |
| 措辞通不通顺 | **模型**（可选，且被数字/因果词校验拦截） | `workflow/nodes.py:1589` |

> **项目设计选择**：模型在整条链上只被允许做两件事——知识答案的改写（还要过引用校验）、以及一句不含数字的措辞润色。两件事失败都只是"不润色"，不影响主流程（`KNOWLEDGE_ERROR` / `LLM_POLISH_SKIPPED`）。

### 3.4 state 是账本，不是聊天记录

`AssistantState` 是一个 `TypedDict`，每个键就是一个"通道"。读代码时请记住三条规则：

1. **默认覆盖**：节点返回的同名键会覆盖旧值（`draft_report` 被 `export` 覆盖成 `final_report` 的内容就是这样）。
2. **声明了 reducer 的才累加**：`messages: Annotated[list, add_messages]`、`trace: Annotated[list[dict], operator.add]`、`errors: Annotated[list[str], operator.add]`。
3. **`sources` 在多处被 `extend` 后整体写回**：`knowledge`、`data`、`compute` 三个节点各自读 `state["sources"]`、追加自己的条目、再整体返回——效果等价于累加，但它靠的是代码自觉，不是 reducer。

> **项目设计选择**：`sources` 没有用 `operator.add`，是为了能按 `(doc_id, chunk_id)` 去重（`_doc_sources` 内部的 `seen` 集合），以及让节点能"整体替换"。代价是：**任何忘记读旧值的节点都会静默丢来源**。这是改代码时要特别小心的地方（第 7 节练习 1 会踩到）。

### 3.5 为什么数字必须由程序注入

报告里的数字如果让模型写，会出现三类事故：算错、编造、以及"看起来合理但和表格对不上"。本项目用三层机制封死：

**第一层：模型拿不到数字。** `_narrative_seed()` 给模型的"种子句"里一个数字都没有（连月份都没有），只给它一句不含数值的话让它改写：

```python
def _narrative_seed(calculation: dict[str, Any]) -> str:
    """给模型润色用的"一句话"种子（不含任何数字，避免模型复述/篡改数字）。"""
    metric = str(calculation.get("metric") or "net_sales")
    dimension = str(calculation.get("dimension") or "region")
    return (
        "请把下面这句话改写得更通顺，不要添加任何数字、日期、百分比，也不要解释原因：\n"
        f"本期与上期的{METRIC_LABELS.get(metric, '净销售额')}存在差异，"
        f"按{DIMENSION_LABELS.get(dimension, '地区')}看各明细的表现并不相同，"
        "具体数值以报告表格为准，解读前请先看数据边界与来源。"
    )
```

**第二层：输出里出现数字就整段丢弃。**

```python
polished = str(text or "").strip()
if not polished:
    return None, []
if DIGITS.search(polished):
    return None, [
        "LLM_POLISH_REJECTED: 模型润色结果包含数字，已整段丢弃；"
        "报告中所有数字始终由程序注入。"
    ]
if any(word in polished for word in CAUSAL_WORDS):
    return None, [
        "LLM_POLISH_REJECTED: 模型润色结果包含因果措辞，已整段丢弃，避免把相关性写成因果。"
    ]
return f"模型润色（仅措辞，未经人工事实核查）：{polished}", []
```

**第三层：报告正文用纯模板渲染。** `render_analysis_report()` 只读 `calculation` 这个"已经算好的字典"，把整数分格式化成金额、把变化率格式化成百分比；模型最多贡献一句被标注了"模型润色（仅措辞，未经人工事实核查）"的闲话。

> **教学简化**：真实报告里"为什么下降"这类归因**没有**做，因为数据里没有因果信息。项目故意把它留空，而不是让模型编一个理由——这正是"因果措辞整段丢弃"这条规则想防的东西。

### 3.6 为什么检索结果和 SQL 结果都要变成 `sources`

一份能被人复核的报告，必须回答两个问题：**这个数字怎么算的**（SQL）和**这个口径谁定的**（文档）。所以 `sources` 是一个混合列表，两种条目的形状完全不同：

| 来源类型 | 由谁写入 | 关键字段 | 用途 |
| --- | --- | --- | --- |
| `type="doc"` | `knowledge_node` → `_doc_sources(citations)` | `doc_id`、`chunk_id`、`title`、`snippet`、`score`、`method`、`ref` | 证明"销售额扣除退款"这个口径有文档依据，`ref` 形如 `[doc_id#chunk_id]` |
| `type="sql"` | `data_node`、`compute_node` → `_sql_source(...)` | `sql`、`params`、`note` | 证明数字来自哪条等价 SQL、参数是什么 |

```python
def _sql_source(sql: str, params: dict[str, Any], *, note: str) -> dict[str, Any]:
    """构造一条 SQL 来源（写进报告第 8 段与 TurnResult.sources）。"""
    return {"type": "sql", "sql": sql, "params": jsonable(params), "note": note}
```

```python
def _doc_sources(items: list[dict[str, Any]]) -> list[dict[str, Any]]:
    """把引用列表转成来源条目，并按 (doc_id, chunk_id) 去重。"""
    seen: set[tuple[str, str]] = set()
    sources: list[dict[str, Any]] = []
    for item in items:
        doc_id = str(item.get("doc_id") or "").strip()
        chunk_id = str(item.get("chunk_id") or "").strip()
        if not doc_id and not chunk_id:
            continue
        key = (doc_id, chunk_id)
        if key in seen:
            continue
        seen.add(key)
        sources.append(
            {
                "type": "doc",
                "doc_id": doc_id,
                "chunk_id": chunk_id,
                "title": str(item.get("title") or ""),
                "snippet": str(item.get("snippet") or "")[:300],
                "score": item.get("score"),
                "method": str(item.get("method") or ""),
                "ref": f"[{doc_id}#{chunk_id}]",
            }
        )
    return sources
```

注意 `_sql_source` 里的 `sql` 字符串是**等价说明**，不是真正执行的语句：项目把 SQL 硬编码成常量（`MONTH_SALES_SQL`、`REFUND_SQL`、`REGION_SQL`、`COMPARE_SQL`），真实执行全部走 `queries.py` 的具名函数。这样报告里展示的 SQL 和实际口径**不会**各自漂移。

> **项目设计选择**：SQL 文本由 `nodes.py` 当常量维护，而不是从 `queries.py` 反推。好处是审计时一眼能看懂"这条 SQL 就是我报告里那段话"；代价是改 `queries.py` 的口径时要同步改常量（第 8.2 节的实验会让你看到两者不一致时的表现）。

## 4. 这个知识在主项目中的位置

### 4.1 一张图看清整轮

```
START
  │
  ▼
understand ──clarify──▶ clarify ──▶ END
  │  ├──knowledge──▶ knowledge ──▶ data
  │  ├──data───────▶ data
  │  └──fail───────▶ fail ──▶ END
  │
 data ──ok──────▶ compute
   ├──retryable──▶ repair ──▶ data（最多 1 次）
   └──其它───────▶ fail ──▶ END

compute ──▶ draft ──▶ review（interrupt 等人工）──approve/edit──▶ export ──▶ END
                                              └──reject─────────▶ END
```

上图的边全部在 `workflow/graph.py` 的 `build_graph()` 里声明；每条条件边的判定函数在 `workflow/routing.py`：

| 判定函数 | 可能的返回值 | 依据 |
| --- | --- | --- |
| `route_after_understand` | `clarify` / `knowledge` / `data` / `fail` | `route_after_understand` 读 `state["route"]`，`status` 属于 `{"failed","budget_exceeded"}` 时强制 `fail` |
| `route_after_data` | `compute` / `repair` / `fail` | 成功→`compute`；错误以 `retryable:` 开头且未修过→`repair`；其余→`fail` |
| `route_after_review` | `export` / `END` | `review.decision` 为 `approve`/`edit`→`export`；`reject`→`END` |

`routing.py` 里三个常量把规则说死了：

```python
UNDERSTAND_ROUTES = ("clarify", "knowledge", "data", "fail")
MAX_REPAIR_ATTEMPTS = 1
TERMINAL_STATUSES = {"failed", "budget_exceeded"}
```

> **项目设计选择**：`repair` 节点**不写库、不做任何修复**，只做一次只读探活（`SELECT 1`）并把"重试过一次"记进 `trace`；真正的重试靠路由回到 `data`。所以"修复失败"永远不会破坏历史数据，最多是多花一步预算。

### 4.3 每个节点读什么、写什么

| 节点 | 读 | 写 | 副作用 |
| --- | --- | --- | --- |
| `understand` | `question`、`last_spec`、`user_id`、`budget` | `spec`、`route`、`clarification`、`status`、`budget`、`trace`，必要时 `last_spec` | 只读元数据（`list_available_months` / `list_regions`），**不占工具预算** |
| `clarify` | `clarification` | `status="clarification"`、`messages`、`trace` | 无 |
| `knowledge` | `question`、`spec`、`sources` | `policy_context`、`knowledge_hits`、`sources`（追加 doc）、`trace`、`errors` | 检索知识库；失败只记 `KNOWLEDGE_ERROR` |
| `data` | `spec`、`sources` | `data_result`、`tables`、`sources`（追加 sql）、`trace`、`errors` | 只读 SQLite |
| `repair` | `trace` | `errors`（带 `retryable:`）、`trace` | 只读探活 `SELECT 1` |
| `compute` | `spec`、`data_result` | `calculation`、`tables`、`chart`、`sources`（追加对比 sql）、`trace`、`errors` | 调用 `compare_months`，无 IO |
| `draft` | `calculation`、`sources`、`policy_context`、`spec`、`question` | `draft_report`、`status="awaiting_approval"`、`trace`、`errors` | 可选调用一次模型（仅润色） |
| `review` | `draft_report`、`calculation` | `status`、`review`、`final_report`、`messages`、`trace`、`budget` | `interrupt()` 挂起；恢复后**不落盘** |
| `export` | `draft_report`、`final_report`、`review` | `export_path`、`final_report`、`status="approved"`、`trace` | **唯一落盘节点**：临时文件 → `fsync` → `os.replace` 原子替换 |
| `fail` | `status`、`errors` | `messages`、`trace` | 无（不依赖 Runtime，保证任何失败都能走到） |

> **项目设计选择**：`export` 是唯一写文件的节点，`review` 在 `interrupt()` 之前只做"纯读 + 纯算"。这条规则来自 checkpointer 的语义——节点恢复时会**从头重跑**（`interrupt()` 返回恢复值后继续），如果 `interrupt()` 前面有写操作，就会重复写。

### 4.4 三个入口，你该用哪个

| 入口 | 一行代码 | 什么时候用 |
| --- | --- | --- |
| `AppRuntime.invoke_turn` | `runtime.invoke_turn(question, thread_id="t1")` | **推荐**。本单元最小实验走这条；它替你装配连接、KB、检查点、图 |
| `runtime.graph.invoke(...)` | `runtime.graph.invoke(state, config=..., context=...)` | 调试单个节点、想自己控制 `initial_state` 时 |
| 直接调底层函数 | `compare_months(conn, "2026-09", "2026-08")` | 写单元测试、验证口径、或者"我就想算个数" |

## 6. 预期输出与关键状态变化

> 下面所有输出都是 **预期（未在本环境执行）**：本环境不能启动 Python 进程，我没有运行过这些命令。数值列写成 `<整数分>` 之类占位符——具体数字由 `bootstrap.py` 生成的数据决定，**不要**把它们抄进任何断言；如果你要核对数值，用 `data/ground_truth.json`。

### 6.1 主问题（一轮走到底）

问题：`2026 年九月销售额比八月变化多少？按地区分解差额，并说明销售额是否扣除了退款。`

```text
预期（未在本环境执行）
status       : awaiting_approval
clarification: ''
source types : ['doc', 'sql']
source count : <整数>   # doc 条数取决于知识命中，sql 条数取决于走了哪些取数函数
interrupt    : report_approval ['approve', 'reject', 'edit']
trace nodes  : ['compute', 'data', 'draft', 'knowledge', 'understand']
report chars : <整数>
------------------------------------------------------------
（报告正文，固定 8 段二级小节：结论 / 关键数字 / 地区差额分解 / 口径与依据 / 数据边界 / 计算过程 / 局限与未验证 / 来源）
```

为什么 `trace nodes` 里**没有** `review`：`review_node` 的 trace 条目写在 `interrupt()` **之后**（第 5.6 节那段代码的顺序），而 `interrupt()` 会抛 `GraphInterrupt` 让图挂起——所以这一轮的快照里还没轮到它。`resume_turn` 之后 `review` 从头重跑、拿到恢复值、才补上这条 trace，随后 `export` 也追加一条。这是"节点恢复 = 从头重跑"最直观的证据。

为什么 `source types` 是 `['doc', 'sql']` 而不是只有 `sql`：问题里出现了"是否扣除了退款"这种口径诉求，命中 `KNOWLEDGE_HINTS`，`understand` 把 `route` 从 `data` 改成了 `knowledge`；`knowledge` 写入 `doc` 条目，`data`/`compute` 再追加 `sql` 条目。**如果知识库没命中**（`insufficient=True`），`citations` 为空，`doc` 就不会出现——这时 `source types` 是 `['sql']`，报告里"口径与依据"段会写明"本轮没有知识库结论"。

### 6.2 追问（同一个 thread 的第二轮）

问题：`那华东地区呢？`

```text
预期（未在本环境执行）
status       : awaiting_approval
clarification: ''
spec.regions : ('R_EAST',)
spec.current_month : 2026-09        # 从 last_spec 继承
spec.previous_month: 2026-08        # 从 last_spec 继承
trace 里会多出: inherit_period_from_last_turn / inherit_regions_from_last_turn
```

这一轮能成立的前提是第 5.4 节那两条继承分支，以及 `initial_state()` **故意不重置** `last_spec`：

- `invoke_turn` 每轮都会调 `initial_state(...)`，它把 `spec`、`data_result`、`calculation`、`draft_report` 等一轮性字段全部清空；
- 但 `last_spec` 不在 `initial_state` 的返回里，所以它由 checkpointer 里上一轮的状态保留下来。

> **项目设计选择**：这是"跨轮上下文"的极简实现——只记住结构化规格，不记住对话原文。好处是可解释（你知道它记了什么）、可测试；代价是复杂的多轮指代（"那个地区""再往前一个月"）需要你扩展 `parse_question`，而不是靠模型理解。

### 6.3 澄清（缺年份）

问题：`九月销售额是多少？`

```text
预期（未在本环境执行）
status       : clarification
clarification: '请补充要分析的时间范围，例如“2026 年九月销售额比八月变化多少”；可用数据范围：2025-01 ~ 2026-09；可用地区：<按你的数据，最多 8 个>'
route        : 'clarify'
trace nodes  : ['clarify', 'understand']
export_path  : None
```

`clarify` 节点只做一件事：把 `clarification` 包成一句人话发出去（`"需要您补充一点信息：..."`），`status="clarification"`，然后 `clarify → END`。**它不猜、不查数、不调模型。**

### 6.4 一轮之内 state 的填充时序

| 时机 | 新填充/更新的字段 | 观察点 |
| --- | --- | --- |
| `initial_state()` | `question`、`thread_id`、`user_id`、`budget`、`status="running"`、`messages`、`trace=[]`、`errors=[]` | `budget={"steps":0,"max_steps":12,"tool_calls":0,"max_tool_calls":8}` |
| `understand` | `spec`、`route`、`clarification`、`status`、`last_spec` | `spec` 里 `current_month=2026-09`、`previous_month=2026-08`、`dimension="region"`、`metric="net_sales"` |
| `knowledge` | `policy_context`、`knowledge_hits`、`sources`(doc)、`trace` | `knowledge_hits` 里每条有 `chunk_id` / `score` / `method` |
| `data` | `data_result`、`tables`、`sources`(sql)、`trace` | `data_result["current"]["net_cents"]` 是整数分 |
| `compute` | `calculation`、`tables`、`chart`、`sources`(sql)、`trace` | `calculation["metric_delta_cents"] == 本期 − 上期`（程序内自校验） |
| `draft` | `draft_report`、`status="awaiting_approval"`、`trace` | `draft_report` 里所有数字都来自 `calculation` |
| `review`（恢复后） | `review`、`final_report`、`messages`、`trace` | `review={"decision":"approve",...}` |
| `export` | `export_path`、`final_report`、`status="approved"` | `final_report` 与磁盘文件**逐字节一致** |
| `fail` | `messages`、`trace` | `status` 保持 `failed` / `budget_exceeded` |

### 6.5 怎么"看见"这些字段，而不是猜

`invoke_turn` 返回的是 `_turn_result()` 组装好的 `TurnResult`，包含 `thread_id / status / answer / report / clarification / interrupt / sources / tables / chart / trace / usage / metrics / errors / export_path / request_id`。三个最省事的检查点：

```python
# 1) 来源够不够、类型对不对
print(sorted({s["type"] for s in turn["sources"]}))
print([s.get("ref") for s in turn["sources"] if s["type"] == "doc"])

# 2) 数字自洽：差额是否等于本期减上期（用 calculation 里的字段）
calc = ...  # 从 runtime 状态里读；也可以直接看审批载荷 interrupt["summary"] 的三行摘要
print(calc["metric_current_cents"], calc["metric_previous_cents"], calc["metric_delta_cents"])

# 3) 失败原因是不是"可读的中文"
print(turn["errors"])
```

> **项目设计选择**：`_turn_result` 里 `trace` 只保留最后 200 条（`[-200:]`）。这不是怕慢，是怕把整条链的 trace 全塞进 HTTP 响应和前端。写测试时如果要断言更早的 trace，请直接读检查点快照，而不是读 `TurnResult`。

## 8. 失败与边界实验（至少 3 个）

> 三条实验都不需要 API Key。命令里的 `OPS_MAX_STEPS` 是 `config.py` 读的环境变量（`DEFAULT_MAX_STEPS = 12`，可用 `OPS_MAX_STEPS` 覆盖；`max_tool_calls` 同理是 `OPS_MAX_TOOL_CALLS`）。如果你的 shell 不认这种写法，用 `$env:OPS_MAX_STEPS="1"`（PowerShell）或 `export OPS_MAX_STEPS=1`（bash）。

### 8.1 预算打满：`max_steps=1`

```bash
OPS_MAX_STEPS=1 uv run python scratch/exp14_invoke_turn.py
```

```text
预期（未在本环境执行）
status       : budget_exceeded
errors       : ['BUDGET_EXCEEDED: 单轮预算已用尽（steps=1/1，tool_calls=0/8），工作流提前结束。...']
answer       : '本轮分析因预算限制提前结束。 BUDGET_EXCEEDED: ... 建议缩小问题范围（例如只问一个地区或一个指标），或调高 OPS_MAX_STEPS / OPS_MAX_TOOL_CALLS 后重试。'
```

机制：`_guard_step()` 的判定是"消耗一步后仍在上限内、**且还剩至少一步给下一个节点**"。所以 `max_steps=1` 时 `understand` 第一步就把自己判死，`_budget_exceeded_update()` 写 `status="budget_exceeded"`，`understand` 额外把 `route` 设成 `"fail"`，直接去 `fail` 节点收敛成一句人话。

**边界结论**：预算是**每个节点**的守卫，不是全局计时器；`max_steps` 太小会连"理解"都过不去，所以调参时要先算清最短路径（`understand → data → compute → draft → review → export` 就已经 6 步）。

### 8.2 数据库不可用：把 `data/ops.db` 改名

```bash
mv data/ops.db data/ops.db.bak
uv run python scratch/exp14_invoke_turn.py
mv data/ops.db.bak data/ops.db    # 记得改回来
```

```text
预期（未在本环境执行）
status : failed
errors : ['METADATA_ERROR: 读取可用月份/地区失败（OperationalError），无法解析问题。']
answer : '本轮分析未能完成。 原因：METADATA_ERROR: ... 可以换一种说法，或先运行 scripts/bootstrap.py 检查演示数据是否就绪。'
```

注意失败发生在**第一个节点**：`understand` 一上来就要读"可用月份/地区"来校验用户说的时间是否在数据范围内，读不到就立刻停——这不是"数据节点失败"，而是"理解失败"，两者在 `errors` 里的前缀不同（`METADATA_ERROR` vs `DATA_ERROR`）。

如果你想看**可重试**路径，把 `data` 节点用的表临时改名（例如 `orders` → `orders_x`）而不动元数据查询：`understand` 仍能解析，`data` 抛 `OperationalError` → 错误带 `retryable:` 前缀 → 走一次 `repair`（`SELECT 1` 探活）→ 回到 `data` 再失败 → `MAX_REPAIR_ATTEMPTS=1` 用完 → `fail`。`trace` 里会看到 `repair` 只出现一次。

### 8.4 审批打回：`reject` 不落盘

## 10. 复盘问题与参考答案、下一步

**Q1：这一轮里，模型到底有没有"选工具"？**

没有。工作流这一侧一次工具选择都没有发生：`understand` 用规则解析决定 `route`，`knowledge`/`data`/`compute` 各自直接调用具名函数。模型只被允许在 `knowledge` 里改写答案（且要过引用校验）、在 `draft` 里润色一句不含数字的话。真正"模型选工具"的是另一条路线（`agent/tools.py` 的 6 个 `@tool` + `create_agent`），两条路线共用底层函数但**不共用一个入口**。

**Q2：为什么 `clarify` 和 `fail` 都直接 `END`，而不回到 `understand`？**

因为回环会让预算和 trace 变得难解释：用户补充信息是**新的一轮 `invoke_turn`**（新 `question`），不是在旧图里打转。`fail` 更不该回环——它代表"这一轮不可能成功了"，回环只会烧预算。所以两个出口都是终态，区别只在 `status`（`clarification` vs `failed`/`budget_exceeded`）。

**Q3：`last_spec` 为什么不放进 `initial_state()`？**

因为它要跨轮存活。`initial_state()` 每次 `invoke_turn` 都会重置一轮性字段（`spec`、`data_result`、`calculation`、`draft_report` 等），而 `last_spec` 留在 checkpointer 的上一轮快照里。**代价**是：换 `thread_id` 就等于换上下文，追问立刻失效（第 8.5 节）。

**Q4：`sources` 为什么不用 `operator.add`，却又要三个节点各自"读旧值再写回"？**

因为需要去重（`_doc_sources` 用 `(doc_id, chunk_id)` 做 key）和整体替换的能力；`operator.add` 只能无脑拼接，重复引用会越堆越多。代价是**靠代码自觉**：任何节点忘记 `list(state.get("sources") or [])` 就会静默丢来源。所以改 `nodes.py` 时，`sources` 相关代码是最需要 review 的地方。

**Q5：如果明天要换一个数据源（比如从 SQLite 换成数仓），你要改哪几层？**

`data/queries.py`（唯一直接写 SQL 的地方）、`domain/metrics.py` 里的连接使用方式、`nodes.py` 里展示用的 SQL 常量（`MONTH_SALES_SQL` 等，它们只是"口径说明"不是执行语句）、`agent/tools.py` 的 `make_tools`（连接类型）。**不用改**：`domain/question.py`、`report/format.py`、`workflow/state.py`、`workflow/routing.py`、`workflow/graph.py`。这就是把"取数"和"编排"分开的价值。
